## Findings

**F1 — Type-violating input returns a verdict instead of a clean input
error.** Case 4: `baselines.naive_value` as a string where a number is required. Expected (test doctrine for
this program + the gateway's `invalid_input` mechanism in
`callpath.ts`): HTTP 422 `{ok:false, error:"invalid_input", field:...}`.
Actual: HTTP 200, verdict `FORECAST_NOT_READY` computed over the garbage values (0 pass / 1 fail / 24 missing). The atom's handler does not validate
manifest field types before evaluation. Disposition: **fix spec filed** —
`verification/fix-specs/forecast-with-ranges-and-scorecard.md`. Retest on redeploy.

Gemini recomputed the full-pass scorecard by hand: MAE=0.0, MAPE=0.0, Bias=0.0 (forecast equals actual in the declared history) and confirmed the range ordering 90 ≤ 100 < 110 — all match the artifact.

Gemini's `expect.failing_checks` for the violations case named sections (`ranges_and_scenarios`, `scorecard_accuracy`) rather than check names; the four checks that actually failed are exactly the checks of those sections that the planted values breach, verified against the raw evidence — not a tester error.
