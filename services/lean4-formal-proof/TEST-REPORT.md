## Findings

**F1 — Type-violating input returns a verdict instead of a clean input
error.** Case 4: `setup` as a string where an object is required, `theorems` as a string where a list is required. Expected (test doctrine for
this program + the gateway's `invalid_input` mechanism in
`callpath.ts`): HTTP 422 `{ok:false, error:"invalid_input", field:...}`.
Actual: HTTP 200, verdict `INSUFFICIENT_EVIDENCE` computed over the garbage values (0 pass / 0 fail / 26 missing). The atom's handler does not validate
manifest field types before evaluation. Disposition: **fix spec filed** —
`verification/fix-specs/lean4-formal-proof.md`. Retest on redeploy.

Gemini recomputed the computed-check counts from the full-pass theorems list: `theorems_evaluated=1`, `theorems_with_sorry=0` — both match the artifact.

**Tester error corrected (1):** Gemini's first design set `definitions.total` to a number (`10` in full-pass, `1` in violations), but SERVICE.md states all fields are booleans unless noted and `definitions.total` is the boolean totality flag. The atom correctly failed `definitions_are_total` on the numeric value, so the first run's full-pass returned `NOT_VERIFIED` (25 pass, 1 fail) — Gemini's initial judgment recorded that as an atom logic bug; verified against SERVICE.md and the raw evidence, it was a case-design error, not an atom defect. The case file was corrected (`definitions.total: true` in both cases), steps 2–3 were re-run, and the corrected run is the evidence of record above: full-pass `VERIFIED` 26/26, violations failing exactly the two planted checks. The superseded first-run judgment is preserved in the work directory history of this lane's notes here; the atom was never at fault on this point.
