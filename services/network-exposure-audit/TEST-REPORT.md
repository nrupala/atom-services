## Findings

**F1 — Type-violating input returns a verdict instead of a clean input
error.** Case 4: `inventory.current` as a string where a boolean is required. Expected (test doctrine for
this program + the gateway's `invalid_input` mechanism in
`callpath.ts`): HTTP 422 `{ok:false, error:"invalid_input", field:...}`.
Actual: HTTP 200, verdict `UNSOUND` computed over the garbage values (0 pass / 1 fail / 26 missing). The atom's handler does not validate
manifest field types before evaluation. Disposition: **fix spec filed** —
`verification/fix-specs/network-exposure-audit.md`. Retest on redeploy.

Gemini verified the check totals: 27 checks reported on each of the full-pass, violations and sparse cases — matching the contract's 27-check count.

**Tester expectation corrected (1):** Gemini's violations case also expected `encrypted_endpoints_have_valid_certs` to fail because the planted endpoint carries `tls_cert_valid=false`. SERVICE.md scopes that check to *encrypted-protocol* endpoints ("encrypted protocols … require `tls_cert_valid`"; `tls_cert_valid` "must be `true` on every encrypted-protocol endpoint"), and the planted endpoint's protocol is plaintext `http` — so the check correctly passes (vacuously) and the endpoint is instead caught by `no_plaintext_protocol_endpoints`. Verified against SERVICE.md and the raw artifact; the expectation, not the atom, was wrong. The input itself was contract-valid and the verdict exact, so no re-run was needed; the correction is recorded here and counted in `tester_errors`.

## Final verdict

**FAIL** — core verdict logic is exact on all three verdict cases,
determinism and MCP/REST parity hold, the stamp is well-formed; the
single defect is F1 (malformed-input handling).
