Bound capability (from the skill): Write production TypeScript — strict mode, no any, typed boundaries with schemas, small honest modules.

A caller submits a declared strict TypeScript engineering record for one TypeScript codebase and receives one deliverable back: a deterministic verdict over that record. One unit of sale = one delivered result.

Several checks are computed from the declared rows and the
declared tsconfig flags, using only the skill's own stated
rules plus the consistency of the declared record itself —
no outside threshold is imported:

- **Boundaries declared:** the declared `boundaries` list
  passes when it is present. An absent list is missing
  evidence. An empty list passes: it declares that the
  codebase has no external boundaries, and the skill requires
  no boundary.
- **Schema validation per boundary:** every declared boundary
  row must declare `schema_validated` true (the skill:
  validate external input — API, storage, env — with a schema
  such as zod/valibot; parse, don't trust). A row with the
  field absent is missing evidence; a row declaring it false
  fails. On an empty list the check passes vacuously.
- **Schema testing per boundary:** every declared row must
  declare `schema_tested` true (the skill's quality gate:
  boundary schemas exist and are tested), under the same
  absent/false/vacuous rules.
- **No boundary name duplicated:** no declared boundary
  `name` may appear on more than one row. A row with `name`
  absent is missing evidence for this check.
- **Modules declared:** the declared `modules` list passes
  when it is present, under the same absent/empty rules.
- **Any-free per module:** every declared module row must
  declare `any_free` true (the skill: no `any` in `src/`),
  under the same absent/false/vacuous rules.
- **Explicit public surface per module:** every declared row
  must declare `explicit_public_surface` true (the skill:
  explicit public surfaces), under the same rules.
- **No module name duplicated:** no declared module `name`
  may appear on more than one row, under the same rules.
- **Strict-flag coverage:** the two skill-named strict flags
  (`strict` and `noUncheckedIndexedAccess`) are counted when
  both are declared: the ratio of the two that are declared
  true. It is null when either flag is absent. The ratio is
  reported only; the bar is the two boolean checks
  themselves, not a coverage percentage.

The output also reports the computed `computed_status`
(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any
of the eight primary computed checks above cannot be
completed), `boundaries_count` and `modules_count` (the
declared list lengths, or null when a list is not declared —
counts are reported as integers, exactly), the row-name lists
`boundaries_without_schema_validation`,
`boundaries_without_schema_tests`, `modules_not_any_free` and
`modules_without_explicit_public_surface` (rows whose field
is present but not true; a row with the field absent is
missing evidence and does not appear),
`duplicate_boundary_names` and `duplicate_module_names`
(names declared on more than one row, in the order their
second occurrence appears), and the coverage ratios
`strict_flag_coverage`, `schema_validation_coverage`,
`schema_test_coverage`, `any_free_coverage` and
`explicit_public_surface_coverage`. **Fixed serialization
rule:** computed ratios are reported as strings with exactly
six decimal places, produced in both implementations by the
same rule — round half up to 6dp,
`floor(v * 1000000 + 0.5) / 1000000`, then format with exactly
six decimals; comparisons use the unrounded values. A ratio
is null when its denominator list is absent or empty (for
`strict_flag_coverage`, when either named flag is absent).
That fixed serialization is what makes the Python and
TypeScript outputs byte-identical.

## Honest scoping

This atom reviews a **declared** strict TypeScript
engineering record — it compiles nothing itself, runs no
tsc, vitest, linter or bundler, inspects no repository or
source file, and does not verify that declared practice was
ever carried out. A codebase is ready *on the caller's
declared evidence*: a record that declares `strict: true`,
no `any` and every boundary schema-tested passes those
checks even if the real codebase did none of it. It is a
completeness and consistency audit of the engineering record
the skill requires, **not a compiler, a type checker, a code
review, or a guarantee that the code is type-safe or
correct**: it never judges whether a declared schema actually
matches the real runtime shape, whether a discriminated union
actually models the real states well, or whether a justified
cast is actually sound — only that the record contains what
the skill's strict TypeScript practice demands, and that its
declared boundary and module rows are internally consistent.

Named exclusions and non-reducible parts (carried as caller
declarations only, never judged): the skill's
write-my-code steps are EXCLUDED by name — converting
JavaScript to TypeScript, writing or rewriting any TypeScript
code, authoring a tsconfig, writing a zod/valibot schema,
designing a discriminated union for a caller's state machine,
refactoring modules or barrel files, fixing a floating
promise, and migrating a JS project to TS are never performed
or emitted; the atom only checks declared
presence/consistency and refuses the skill's anti-patterns as
red-line declarations. Also excluded: no numeric thresholds
at all (the skill states none — see the declined list above);
no live verification of any declared fact; no judgment of
practice *quality* — whether the strictness, typing or module
design is adequate for the real codebase is the caller's
declaration, checked only for declared presence and
consistency.
