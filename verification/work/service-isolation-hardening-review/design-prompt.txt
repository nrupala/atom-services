Several checks are computed from the declared rows, using only
the skill's own stated rules plus the consistency of the
declared record itself — no outside threshold is imported:

- **Rostered services declared:** the declared `services` list
  passes when it is present. An absent list is missing
  evidence. An empty list passes: it declares that the record
  rosters no services, and the skill requires no minimum fleet
  size.
- **Dedicated user per rostered service:** every declared
  service row must declare `dedicated_user_assigned` true
  (the skill: "one service, one non-login system user"). A row
  with the field absent is missing evidence; a row declaring
  it false fails. On an empty list the check passes vacuously.
- **Filesystem access scoped per rostered service:** every
  declared service row must declare `filesystem_access_scoped`
  true (the skill: "no cross-service file access"), under the
  same absent/false/vacuous rules.
- **Egress restricted per rostered service:** every declared
  service row must declare `egress_restricted` true (the
  skill: "restrict outbound"), under the same rules.
- **No rostered service name duplicated:** no declared service
  `name` may appear on more than one row. A row with `name`
  absent is missing evidence for this check.

The output also reports the computed `computed_status`
(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any of
the five primary computed checks above cannot be completed),
`services_count` (the declared list length, or null when the
list is not declared — counts are reported as integers,
exactly), the row-name lists `services_without_dedicated_user`
(services whose dedicated-user field is present but not true;
a service with the field absent is missing evidence and does
not appear), `services_without_filesystem_scope` and
`services_without_egress_restriction` (same rule for their
fields), `duplicate_service_names` (names declared on more
than one row, in the order their second occurrence appears),
and the coverage ratios `dedicated_user_coverage` (services
with a dedicated user ÷ declared services),
`filesystem_scope_coverage` and `egress_restriction_coverage`.
**Fixed serialization rule:** computed ratios are reported as
strings with exactly six decimal places, produced in both
implementations by the same rule — round half up to 6dp,
`floor(v * 1000000 + 0.5) / 1000000`, then format with exactly
six decimals; comparisons use the unrounded values. A ratio
is null when its denominator list is absent or empty. That
fixed serialization is what makes the Python and TypeScript
outputs byte-identical.

The skill states no numeric threshold at all — its demands are
qualitative declarations the record makes, not bars the atom
can set. Quantities are computed and reported; the only bar on
the computed rows is completeness over the caller's own
declared rows, exactly as stated above. Declined thresholds,
named: a CPU, memory or IO quota value under cgroups v2, or a
percentage-of-host resource bar; a timeout duration in
seconds; a restart limit count or restart interval; a ulimit
value for any resource; an egress destination count, or a
named list of permitted destinations beyond restricted-as-
declared; a number of escape/abuse cases that must be
exercised, or a pass rate for them; a MAC denial count or
audit frequency; a syscall list beyond the skill's own
`@system-service` filter class as declared; a capability list
beyond minimal / bounding-set-restricted as declared; a
`ReadWritePaths` path count beyond only-what's-needed as
declared; a log-retention period for exec/spawn events; a
minimum number of rostered services; a criterion for when
kernel isolation is "required" beyond the caller's declaration
that a microVM is used where it is; a rule for when Windows
equivalents are in scope beyond the caller's declaration.

The verdict is one of
`SERVICE_ISOLATION_HARDENING_REVIEW_HARDENED` (all 39 checks

## Honest scoping

This atom reviews a **declared** service-isolation record — it
probes no live system, reads no unit file, inspects no
process, namespace, cgroup or MAC profile, runs no sandbox or
escape test, and does not verify that any declared hardening
was ever applied. A fleet is hardened *on the caller's
declared evidence*: a record that declares `NoNewPrivileges`,
a dedicated user per service, and exercised escape cases
passes those checks even if the real host did none of it. It
is a completeness and consistency audit of the isolation
record the skill requires, **not a penetration test, a
sandbox-escape assessment, a host audit, or a guarantee that
any service is actually isolated**: it never judges whether a
declared directive is correctly valued in the real unit file,
whether a MAC profile is well-written, whether an escape case
was competently designed, or whether the isolation design is
adequate for the real threat — only that the record contains
what the skill's method, quality gates and red lines demand,
and that its declared service rows are internally consistent.

Named exclusions and non-reducible parts (carried as caller
declarations only, never judged): no numeric thresholds at all
(the skill states none — see the declined list above); no live
verification of any declared fact; no judgment of hardening
*quality* — whether the directive values, capability set,
egress destinations or MAC profile are adequate for the real
services is the caller's declaration, checked only for
declared presence and consistency; the skill's house rule on
container runtimes (no Docker in application code, Podman only
as a last resort) is context for the method, not a check —
this atom takes no position on any specific runtime a caller
uses, and no check derives from it.
