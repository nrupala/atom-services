# Technical documentation pack — `technical-documentation-pack`

**Deliverable type:** DELIVERABLE. This atom sells the deliverable it produces — a bounded judgment artifact — never the underlying knowledge itself.

## What it delivers

Bound capability (from the skill): Write documentation that gets used — READMEs, runbooks, API docs, decision records, changelogs, kept close to source.

A caller submits the inputs the bound skill works on and receives one deliverable back, in the contract's output shape (see `contract.yaml`). One unit of sale = one delivered result. In this atom's deterministic form, the caller submits a **declared technical documentation production record** for one product/system and receives the documentation audit verdict as the deliverable: the atom writes no documentation, opens no document and verifies no doc against the real product (see Honest scoping).

## Buyer

First buyer hypothesis (from register data; not yet market-tested): teams and agents working in Writing & documents who need this deliverable on demand and would rather buy it per use than build or staff the capability themselves.

## Self-use (R3 — passed)

Our own workflow that calls it: **READMEs and runbooks for products**. Wright is an internal caller on this atom (zero price, metered to the internal cost ledger — see `rails/billing.md`).

Nineteen checks are computed from the declared rows and
declared versions, using only the skill's own stated rules
plus the consistency of the declared record itself — no
outside threshold is imported:

- **Documentation set declared:** the declared `documents`
  list passes when it is present and names at least one
  document. An absent list is missing evidence; an empty list
  fails — it declares no documentation set at all.
- **Document ids unique:** no declared `doc_id` may appear on
  more than one row. A row with `doc_id` absent is missing
  evidence for this check.
- **Document kind recognised:** every declared document's
  `doc_kind` is one of `readme`, `runbook`, `api_doc`,
  `decision_record`, `changelog` — the artifacts the skill
  names — plus `reference`, `how_to`, `conceptual`, the
  reader-task groupings for guide and reference material in
  the set. Any other value fails and is named in
  `technical_documentation_docs_with_invalid_kind`.
- **Source location per document:** every declared document
  declares a non-empty `source_location` (docs-as-code: docs
  live with the source they describe). A row with the field
  absent is missing evidence; a row declaring an empty
  location fails and is named in
  `technical_documentation_docs_without_source_location`.
- **Source of truth per document:** every declared document
  declares a non-empty `source_of_truth` — the contract,
  source or record it is generated from or verified against.
  A row with the field absent is missing evidence; a row
  declaring an empty source of truth fails and is named in
  `technical_documentation_docs_without_source_of_truth`.
- **Config options declared:** the declared `config_options`
  list passes when it is present and names at least one
  option. An absent list is missing evidence; an empty list
  fails (see Honest scoping for the no-config boundary).
- **Config option ids unique:** no declared `option_id` may
  appear on more than one row.
- **Default per config option:** every declared config option
  declares a non-empty `default_value` (the skill's quality
  gate: every config option documented with its default). A
  row declaring an empty default fails and is named in
  `technical_documentation_config_options_without_default`.
- **Every config option documented:** every declared config
  option row declares `documented: true`. A row declaring it
  false fails and is named in
  `technical_documentation_config_options_not_documented`.
- **Endpoints declared:** the declared `endpoints` list
  passes when it is present and names at least one endpoint.
  An absent list is missing evidence; an empty list fails
  (see Honest scoping for the no-API boundary).
- **Endpoint ids unique:** no declared `endpoint_id` may
  appear on more than one row.
- **Working example per endpoint:** every declared endpoint
  row declares `has_working_example: true` (the skill: one
  working example per endpoint). A row declaring it false
  fails and is named in
  `technical_documentation_endpoints_without_working_example`.
- **Endpoint example verified against contract:** every
  declared endpoint row declares
  `example_verified_against_contract: true`. A row declaring
  it false fails and is named in
  `technical_documentation_endpoints_with_unverified_example`.
- **Every endpoint documented in a declared doc:** every
  declared endpoint's `documented_in_doc_id` names one of the
  declared documents. An endpoint with the field absent, or a
  record with the documents list absent, is missing evidence;
  an endpoint naming an undeclared document fails and is
  named in
  `technical_documentation_endpoints_with_unknown_doc_reference`.
- **Decision records declared:** the declared
  `decision_records` list passes when it is present and names
  at least one record. An absent list is missing evidence; an
  empty list fails (see Honest scoping).
- **Decision record ids unique:** no declared `adr_id` may
  appear on more than one row.
- **Every decision record cross-linked from code:** every

(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any

completed), `documentation_set_docs_count`,
`documentation_config_options_count`,
`documentation_endpoints_count` and
`documentation_decision_records_count` (the declared list
lengths, or null when a list is not declared — counts are
reported as integers, exactly), the duplicate-id lists
`duplicate_technical_documentation_doc_ids`,
`duplicate_technical_documentation_config_option_ids`,
`duplicate_technical_documentation_endpoint_ids` and
`duplicate_technical_documentation_decision_record_ids`, the
row-name lists named in the computed checks above, and the
ratios `doc_source_of_truth_ratio` (documents with a declared
source of truth ÷ declared documents),
`config_option_documentation_ratio` (config options both
declaring a default and declared documented ÷ declared
options), `endpoint_worked_example_ratio` (endpoints both
carrying a working example and declaring it verified against
the contract ÷ declared endpoints) and
`decision_record_cross_link_ratio` (decision records declared
cross-linked from code ÷ declared records). **Fixed
serialization rule:** computed ratios are reported as strings
with exactly six decimal places, produced in both
implementations by the same rule — round half up to 6dp,
`floor(v * 1000000 + 0.5) / 1000000`, then format with exactly
six decimals. A ratio is null when its denominator list is
absent or empty. That fixed serialization is what makes the
Python and TypeScript outputs byte-identical.

The skill states no numeric threshold at all — its demands
are a complete README skeleton, docs-as-code with a named
source of truth, contract-verified API docs with a working
example per endpoint, cross-linked decision records, docs
reviewed and tested like the product, plain language, and a
continuously kept changelog, not bars the atom can set.
Quantities are computed and reported; the only bars on the
computed rows are exact completeness and cross-reference
consistency over the caller's own declared rows, exactly as
stated above. Declined thresholds, named: a minimum or
maximum number of documents, config options, endpoints or
decision records beyond at least one each; a reading-level,
sentence-length or jargon-density bar for plain language
(checked as declarations only); a documentation-coverage
percentage for config options, endpoints or features beyond
exact completeness over the declared rows; an example
correctness bar beyond declared verification against the
contract (the atom receives no contract and no example text
and verifies nothing against the world); a freshness interval
in days for screenshots, commands or any document; a
changelog-entry format or length bar; a versioning-scheme bar
beyond exact equality of the two declared version strings;
any judgment that the documentation is good, clear or useful
(only that its declared production record contains what the
skill requires).

The verdict is one of `TECHNICAL_DOCUMENTATION_SOUND` (all
46 checks pass), `TECHNICAL_DOCUMENTATION_NOT_SOUND` (any
check fails), or `INSUFFICIENT_EVIDENCE` (nothing fails but
evidence is missing), across eight sections:
readme_and_doc_set_structure, docs_as_code_and_source_of_truth,
api_docs_and_worked_examples, decision_records_and_cross_links,

## Honest scoping

This atom reviews a **declared** technical documentation
production record — it writes no documentation, opens no
document, runs no quickstart, executes no example, fetches no
contract and verifies no document against the real product.
A documentation set is sound *on the caller's declared
evidence*: a record that declares its quickstart tested, its
examples verified and its versions matching passes those
checks even if the real documentation work did none of it. It
is a completeness and consistency audit of the documentation
record the skill requires, **not a documentation service, a
doc review, or a guarantee that the documentation is accurate
or good**: it never judges whether a declared source of truth
actually supports the document that cites it, whether a
quickstart actually works, whether the writing is clear, or
whether the docs should be published — only that the record
contains what the skill's method, quality gates and red lines
demand, and that its declared rows are internally consistent.

Named exclusions and non-reducible parts (carried as caller
declarations only, never performed or judged): writing or
rewriting any document itself; generating API docs from a
contract itself; running the quickstart or any worked example
itself; reviewing document prose itself; and maintaining the
changelog itself — each is EXCLUDED by name from this atom,
which audits only the declared record of those steps.
Boundary cases, named: a product/system with genuinely no
config options, no API endpoints, or no decision records
cannot pass this record format's corresponding list-declared
check (the format requires at least one row in each declared
list — such a system is outside this atom's computed reach,
not failed on its merits).

Design EXACTLY 4 cases:
1. kind "full-pass": an input manifest that satisfies every requirement the
   documents state, so the atom must return its PASS outcome (the pass
   verdict/status named in the documents).
2. kind "violations": a manifest of the same shape whose values are present
   but wrong in specific ways, so the atom must return its FAIL outcome and
   the checks covering those wrong values must fail. List the check names
   (as named in the documents/output format) you expect to fail.
3. kind "sparse": a manifest with only one or two fields present, so the
   atom must return its INSUFFICIENT_EVIDENCE outcome (or the equivalent
   named in the documents).
4. kind "malformed": a manifest with clear TYPE violations (e.g. a string
   where an object or list is required, a number where a boolean is
   required), so the atom must answer a clean input error (HTTP 422),
   never a 500 and never a verdict.

Inputs must follow the documented input format exactly (field names,
nesting, value types) — you are testing the atom, so your valid cases must
be genuinely valid per the documents. For computed/report atoms (whose
output is a computed artifact with a status such as complete / partial /
insufficient_evidence), adapt: full-pass = a complete well-formed input
expecting the complete status; violations = an input whose data violates
documented consistency rules expecting the documented failure/partial
behaviour; sparse = a minimal input expecting insufficient_evidence;
malformed = type violations expecting HTTP 422. Where the atom computes
numbers, add "computed_spot_checks" to the full-pass expect: a short list
of quantities the judge can recompute from the input by hand.

Return JSON only, exactly this shape:
