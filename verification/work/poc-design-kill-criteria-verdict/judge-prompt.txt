# Poc design kill criteria verdict — `poc-design-kill-criteria-verdict`

**Deliverable type:** VERDICT. This atom sells the verdict it produces — a bounded judgment artifact — never the underlying knowledge itself.

## What it delivers

Bound capability (from the skill): Validate ideas with proof-of-concept work — hypothesis, success/kill criteria, timebox, evidence, decision.

A caller submits the inputs the bound skill works on and receives one verdict back, in the contract's output shape (see `contract.yaml`). One unit of sale = one delivered result.

## Buyer

First buyer hypothesis (from register data; not yet market-tested): teams and agents working in Thinking & decisions who need this verdict on demand and would rather buy it per use than build or staff the capability themselves.

## Self-use (R3 — passed)

Our own workflow that calls it: **Spike-then-commit product architecture decisions**. Wright is an internal caller on this atom (zero price, metered to the internal cost ledger — see `rails/billing.md`).

## Inputs — the POC design manifest

The caller submits one JSON manifest: a declared proof-of-concept
DESIGN record for one POC, made before the run — the question,
the criteria, the timebox window and the scope as the skill
requires them to be defined upfront. Every field below is read
by the named section's checks. A field **absent** = evidence
missing (`INSUFFICIENT_EVIDENCE`); a field present but false /
invalid = the check fails (`POC_DESIGN_NOT_SOUND`). All fields
are booleans unless noted.

| Field | Read by |

| `design.uncertainty_to_reduce_named` (boolean) | design_premise |
| `design.answer_changes_plan_declared` (boolean) | design_premise |
| `design.uncertainty_reduction_purpose_declared` (boolean) | design_premise |
| `design.design_record_completed_before_run` (boolean) | design_premise |
| `design.evaluates_vendor_or_tool` (boolean; the applicability gate for the house-stack-fit check below) | criteria_row_consistency |

| `criteria[].name` (string; names the row in the computed outputs) | criteria_row_consistency |
| `criteria[].kind` (string; must be one of the two kinds the skill names — `success` or `kill` — per row) | criteria_row_consistency |

| `criteria[].declared_before_run` (boolean) | criteria_row_consistency |

The house-stack-fit check is gated on the declared
applicability flag, exactly as declared:
`vendor_evaluation_applicability_declared` passes whenever
`design.evaluates_vendor_or_tool` is present (either value).
The gated check is **missing** when the gate or the criteria
list is absent, **passes as not applicable** when the gate is
declared `false` (whatever the rows declare), and when the
gate is declared `true` passes only when at least one
criterion row declares `assesses_house_stack_fit: true`.

Several checks are computed from the declared rows and the
declared window, using only the skill's own stated rules plus
the consistency of the declared record itself — no outside
threshold is imported:

- **Criteria declared:** the declared `criteria` list passes
  only when it is present and non-empty; an absent list is
  missing evidence, an empty list fails.
- **Kind per criterion:** every declared criterion row's
  `kind` must be one of the two kinds the skill names
  (step 2: "success AND kill criteria"). A row with the field
  absent is missing evidence; any other string fails.
- **Both kinds present:** at least one declared row must be a
  success criterion and at least one a kill criterion. A set
  of rows of only one kind fails the missing kind's check.
- **Condition per criterion:** every declared criterion row
  must declare `condition_stated: true` — the success bar or
  kill trigger is written, not implied. A row with the field
  absent is missing evidence.
- **Declared before the run per criterion:** every declared
  criterion row must declare `declared_before_run: true`. A
  row with the field absent is missing evidence.
- **No criterion name duplicated:** no declared criterion
  `name` may appear on more than one criterion row. A row
  with `name` absent is missing evidence for this check.
- **Timebox window dates valid:** the declared `start_date`
  and `end_date` must both be real calendar dates in strict
  ISO `YYYY-MM-DD` form (an impossible date such as
  `2027-02-30` fails). An absent date is missing evidence.
- **Timebox end after start:** the declared end date must
  fall after the declared start date — the window has a
  positive length. Its length itself is never judged.
- **Scope items declared:** the declared `scope_items` list
  passes only when it is present and non-empty.
- **Critical path per scope item:** every declared scope row
  must declare `on_critical_path: true` (the skill: "scope is
  the critical path, nothing more"). A row with the field
  absent is missing evidence.
- **No scope name duplicated:** no declared scope `name` may
  appear on more than one scope row. A row with `name`
  absent is missing evidence for this check.

The output also reports the computed `computed_status`
(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any
of the thirteen primary computed checks above cannot be
completed), `criteria_count`, `success_criteria_count` and
`kill_criteria_count` (the declared list length and per-kind
row counts, or null when the list is not declared — counts
are reported as integers, exactly), the row-name lists
`criteria_without_condition` (criteria whose field is present
but not true; a criterion with the field absent is missing
evidence and does not appear), `criteria_not_declared_before_run`
(criteria whose field is present but not true),
`criteria_with_invalid_kind` (criteria whose kind is present
but neither `success` nor `kill`) and
`duplicate_criterion_names` (criterion names declared on more
than one row, in the order their second occurrence appears),
the declared window as `timebox_start_date` /
`timebox_end_date` (the declared strings, or null when
absent) and `timebox_duration_days` (end minus start in
whole days — negative when the window is inverted — or null
when either date is absent or not a real date),
`scope_items_count`, `scope_items_off_critical_path` (scope
items whose field is present but not true),
`duplicate_scope_item_names`, and the three coverage ratios
`condition_stated_coverage` (criteria stating a condition ÷
declared criteria), `declared_before_run_coverage` (criteria
declared before the run ÷ declared criteria) and
`critical_path_coverage` (scope items on the critical path ÷
declared scope items). **Fixed serialization rule:**
computed ratios are reported as strings with exactly six
decimal places, produced in both implementations by the same
rule — round half up to 6dp, `floor(v * 1000000 + 0.5) /
1000000`, then format with exactly six decimals; comparisons
use the unrounded values. A ratio is null when its
denominator list is absent or empty. That fixed
serialization is what makes the Python and TypeScript outputs
byte-identical.

The skill states no numeric pass/fail threshold — its design
demands are qualitative declarations the record makes, not
bars the atom can set. Quantities are computed and reported;
the only bars on the computed rows are completeness over the
caller's own declared rows, both criterion kinds being
present, and the window's internal ordering, exactly as
stated above. Declined thresholds, named: a maximum timebox
length in days or a rule that the window must be "days, not
weeks" enforced as a day count (the skill says the timebox
is a hard limit in days, not weeks — it states no number, so
the declared duration is reported, never capped); a budget
or cost bar for the POC; a number of success or kill
criteria a design must contain beyond at least one of each
kind and the declared lists being non-empty; a minimum
number of scope items; a coverage percentage below
completeness; any required wording, length, or numeric form
for a criterion's stated condition (only that a condition is
declared stated is checked — its content is the caller's).

The verdict is one of `POC_DESIGN_SOUND` (all 22 checks
pass), `POC_DESIGN_NOT_SOUND` (any check fails), or
`INSUFFICIENT_EVIDENCE` (nothing fails but evidence is
missing), across five sections: design_premise,
criteria_row_consistency, timebox_window,
scope_row_consistency, production_boundary_by_design.

## Distinct ground

The nearest deployed sibling is `buyer-test-card`, built
from the same bound skill (`poc-validation`) and live on
Conduit. That atom audits a **completed** POC record at
whole-record level: global attestations that a hypothesis
was written and single and in capability-under-constraints
form, that success/kill criteria were written before the
start and agreed by the decision owner, a timebox limit in
days compared arithmetically against elapsed days, global
evidence attestations (measurements, numbers over
impressions, stubs and mocks recorded), findings-memo /
decision-logged / not-tested-list attestations, and the
finished record's decision (adopt / adapt / abandon) and
disposition (disposable / slated-for-hardening) vocabulary.
This atom sits one stage earlier and shares **zero checks**
with it — no field, check, or computed value is shared:
every check here is a design-stage question over the record
made **before the run** — the uncertainty to be reduced is
named, the answer is declared to change the plan, the
criteria exist as individual **rows** whose kinds cover both
success and kill, whose conditions are stated, which are
each declared before the run, and whose names are not
duplicated; a vendor/tool evaluation, when declared,
carries a house-stack-fit criterion row (the skill's "When
to use" case buyer-test-card never checks); the timebox is
a declared start/end **window** whose dates are real and
ordered (no elapsed time exists yet at design time, and none
is compared); the scope exists as individual rows each
declared on the critical path; and the production boundary
is checked as design **intentions** (no direct-production
use planned, no open-ended design, no POC-success-as-
readiness planned), not as post-hoc events. The boundary is:
design intent and row/window consistency declared before
the run here; the completed record's attestations, elapsed
arithmetic and outcome vocabulary there. No other live or
staged sibling audits a POC design record;
`delivery-plan-preparation` prepares delivery plans with
phases, milestones and dependencies — a delivery record,
not a POC design — and shares no check with this atom.

## Honest scoping

This atom reviews a **declared** POC design record — it
designs no POC itself, runs no POC, writes no code, collects
no evidence, and does not verify that a declared criterion,
window, or scope item was ever honoured. A design is sound
*on the caller's declared evidence*: a record that declares
its criteria rows complete, its window ordered, and no
production gradient planned passes those checks even if the
real POC was never run that way. It is a completeness and
consistency audit of the design record the skill requires,
**not POC execution, an idea review, or regulated
professional advice of any kind (engineering, financial,
medical, or legal)**: it never judges whether the idea is
worth pursuing, whether the hypothesis is true, whether the
named success bars or kill triggers are the right ones, or
whether the POC will work — only that the design record
contains what the skill's method, quality gates, and red
lines demand at design time, and that its declared rows and
window are internally consistent.

Named exclusions and non-reducible parts (carried as caller
declarations only, never judged): no numeric thresholds
beyond the skill's own stated rules (see the declined list
above); no live verification of any declared fact; no
judgment of design *quality* — whether the uncertainty is
the right one, the criteria are well chosen, or the window
is realistic is the caller's declaration, checked only for
declared presence and consistency; the skill's post-run
steps (evidence actually gathered, the findings memo, the
adopt / adapt / abandon decision and its logging, routing an
adoption through the full team process) are the completed
record's ground — `buyer-test-card`'s — and are deliberately
not re-checked here; whether a criterion's stated condition
is measurable in practice is a caller declaration — only
its declared statedness is checked.
