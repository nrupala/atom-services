# Claim evaluation review — `claim-evaluation-review`

**Deliverable type:** REVIEW. This atom sells the review it produces — a bounded judgment artifact — never the underlying knowledge itself.

## What it delivers

Bound capability (from the skill): Think clearly under pressure — evidence hierarchy, base rates, steelmanning, fallacy checks, calibration.

A caller submits the inputs the bound skill works on and receives one review back, in the contract's output shape (see `contract.yaml`). One unit of sale = one delivered result.

## Buyer

First buyer hypothesis (from register data; not yet market-tested): teams and agents working in Thinking & decisions who need this review on demand and would rather buy it per use than build or staff the capability themselves.

## Self-use (R3 — passed)

Our own workflow that calls it: **Pitch and claim evaluations**. Wright is an internal caller on this atom (zero price, metered to the internal cost ledger — see `rails/billing.md`).

## Inputs — the claim-evaluation-review manifest

This atom does not evaluate a claim and exercises no judgment
of its own. The caller submits one JSON manifest declaring a
claim-evaluation artifact — a declared claim set, its
evidence-hierarchy and conflict record, its base-rate /
reference-class record, its steelman and fallacy spot-check
record, its calibration record, and its second-order and
written-judgment record — and the atom validates that artifact
deterministically. This is the claim-evaluation REVIEW over a
declared claim set, built from the bound skill's claim-evaluation
method (its eight method steps, four quality gates and three
red lines); it is not the narrower base-rate card that shares
the same bound skill. Every field below is read by the named
section's checks. A field **absent** = evidence missing
(`INSUFFICIENT_EVIDENCE`); a field present but false / invalid =
the check fails (`CLAIM_EVALUATION_NOT_COMPLETE`). All fields
are booleans unless noted.

Eight checks are computed from the declared values, using only
what the skill itself states plus the arithmetic of the declared
numbers — no outside threshold is imported:

- **Claim entries:** every declared claim entry passes the
  entries check only when it carries a non-empty `label` string
  and all four entry booleans. A missing or empty `claims` list
  is missing evidence; an incomplete entry makes all four
  claim-set checks missing (the set cannot be evaluated whole).
  The output reports `claims_evaluated` (the count of complete
  claim entries).
- **All claims restated precisely:** passes only when every
  complete claim entry declares `restated_precisely` true
  (quality gate: "Claims restated precisely").
- **Supporting AND refuting evidence sought:** passes only when
  every complete claim entry declares both
  `supporting_evidence_sought` and `refuting_evidence_sought`
  true (quality gate: "supporting AND refuting evidence
  sought").
- **Evidence presence assessed:** passes only when every
  complete claim entry declares `evidence_presence_assessed`
  true (method step 1: "Is any actually present?"). Whether
  evidence is in fact present for a claim is not judged — only
  that its presence was assessed, per claim.
- **Base-rate percent range:** method step 3 states a base rate
  for a reference class. The declared
  `base_rates.base_rate_percent` is a percent, so it passes
  only inside 0–100 inclusive — the definition of a percent,
  not a judged level. No base-rate value is imposed (see
  thresholds declined). The output reports it as
  `base_rate_percent` (null when no number is declared).
- **Fallacy coverage:** method step 5 names the spot-check —
  ad hominem, straw man, false dilemma, appeal to
  authority/antiquity, survivorship stories, motivated
  reasoning, cherry-picked windows. The slash in the skill's
  "authority/antiquity" separates two named appeals, so the
  stated set is eight tokens: `ad_hominem`, `straw_man`,
  `false_dilemma`, `appeal_to_authority`, `appeal_to_antiquity`,
  `survivorship_stories`, `motivated_reasoning`,
  `cherry_picked_windows`. The declared
  `fallacy_screen.fallacies_checked` list passes only when it
  contains all eight; unknown entries do not count toward
  coverage. A missing list is missing evidence; an empty list
  is present and fails. The output reports the omitted stated
  entries as `fallacies_not_checked` (null when no list is
  declared). Entries are validated as strings only, never
  enum-checked — coverage is a verdict check, not a type error.
- **Confidence percent range:** method step 6 states confidence
  as a percent ("80% sure"). The declared
  `calibration.confidence_percent` therefore passes only inside
  0–100 inclusive — again the definition of a percent. The
  skill's 80% is an example of stating confidence, **not** a
  required level, so no confidence level is imposed. The output
  reports it as `confidence_percent` (null likewise).
- **Calibration hit rate:** method step 6 states "track hit
  rate". The declared `calibration.declared_hit_rate_percent`
  therefore passes only when it equals
  `calibration.outcomes_correct` / `calibration.outcomes_total`
  × 100, with a positive total (a zero total fails — no hit
  rate exists). No hit-rate level, band width, or minimum
  outcome count is imposed — only the arithmetic is re-derived.
  The output reports `computed_hit_rate_percent` and
  `hit_rate_difference` (declared minus computed, null when
  either cannot be computed).

That is eight computed checks counting claim entries; the
`computed_status` outcome is taken over the other seven.

**Fixed serialization rule:** computed amounts and ratios are
reported as strings with exactly six decimal places, produced in
both implementations by the same rule — round half up to 6dp,
`floor(v * 1000000 + 0.5) / 1000000`, then format with exactly six
decimals; computed comparisons compare the fixed-6dp difference
to zero. That fixed serialization is what makes the Python and
TypeScript outputs byte-identical.

The output also reports the computed `computed_status`
(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any of
the seven computed checks cannot be completed).

The verdict is one of `CLAIM_EVALUATION_COMPLETE` (all 26 checks
pass), `CLAIM_EVALUATION_NOT_COMPLETE` (any check fails), or
`INSUFFICIENT_EVIDENCE` (nothing fails but evidence is missing),
across six sections: claim_set_and_evidence,
evidence_hierarchy_and_conflicts, base_rates_and_reference_class,
steelman_and_fallacy_screen, calibration,
second_order_and_judgment.

## Honest scoping

This atom audits a **declared** claim-evaluation artifact — it
does not read the underlying claims, pitches, articles or
evidence, verify that a declared value is true, or decide
whether any claim is true, well-supported, or worth acting on.
The register's named doubt for this atom — overlaps
critical-reasoning — is answered by this framing: this atom is
the claim-set review from the critical-thinking method (claim →
evidence over a set, hierarchy, base rates, steelman, fallacy
spot-check, calibration, second-order effects, written
judgment), not an argument-anatomy audit and not a base-rate
card. An artifact is complete *on the caller's declared
evidence* even if its underlying claims are false. It is a
completeness and consistency audit, **not a claim verdict**: it
never decides whether the evidence actually supports a claim,
whether the steelman was well built, whether the reference
class was the right one, or whether the stated confidence was
warranted.

**Thresholds declined (named explicitly):** no minimum number
of claims in the set (the skill states none — a single-claim
set can pass); no base-rate level imposed and no judgment that
a base rate is high or low (the skill states no number); no
confidence level required (the skill's "80% sure" is an
example, not a threshold) and no overconfidence threshold or
gap between confidence and hit rate imposed (the skill says
"most find they're overconfident" but states no gap number);
no hit-rate level, confidence-band width, or minimum number of
tracked outcomes imposed (only that a total be positive so the
declared hit rate can be re-derived); no minimum evidence tier
required (the skill states the hierarchy order — measurements/
data > documents/logs > expert synthesis > hearsay — but
mandates no tier as a pass mark, so only that ranking was
applied is checked); no fallacy-severity or count tolerance
(coverage is the skill's exact stated set); no judgment length
(the skill says "short" but states no word count); no
second-order horizon (the skill names the effect kinds, not a
timeframe).

Named exclusions: no evaluation of any claim from raw source
material; no verification of any declared evidence, base rate,
confidence, or outcome count; no truth, support, steelman-quality,
reference-class-choice, or confidence-warrantedness judgment;
no live verification of any declared fact.

1. kind "full-pass": an input manifest that satisfies every requirement the
   documents state, so the atom must return its PASS outcome (the pass
   verdict/status named in the documents).
2. kind "violations": a manifest of the same shape whose values are present
   but wrong in specific ways, so the atom must return its FAIL outcome and
   the checks covering those wrong values must fail. List the check names
   (as named in the documents/output format) you expect to fail.
3. kind "sparse": a manifest with only one or two fields present, so the
   atom must return its INSUFFICIENT_EVIDENCE outcome (or the equivalent
   named in the documents).
4. kind "malformed": a manifest with clear TYPE violations (e.g. a string
   where an object or list is required, a number where a boolean is
   required), so the atom must answer a clean input error (HTTP 422),
   never a 500 and never a verdict.

Inputs must follow the documented input format exactly (field names,
nesting, value types) — you are testing the atom, so your valid cases must
be genuinely valid per the documents. For computed/report atoms (whose
output is a computed artifact with a status such as complete / partial /
insufficient_evidence), adapt: full-pass = a complete well-formed input
expecting the complete status; violations = an input whose data violates
documented consistency rules expecting the documented failure/partial
behaviour; sparse = a minimal input expecting insufficient_evidence;
malformed = type violations expecting HTTP 422. Where the atom computes
numbers, add "computed_spot_checks" to the full-pass expect: a short list
of quantities the judge can recompute from the input by hand.
