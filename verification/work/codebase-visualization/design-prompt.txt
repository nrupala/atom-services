# Codebase visualization — `codebase-visualization`

**Deliverable type:** DELIVERABLE. This atom sells the deliverable it produces — a bounded judgment artifact — never the underlying knowledge itself.

## What it delivers

Bound capability (from the skill): See the codebase — diagrams-as-code, dependency and call graphs, architecture maps, history views.

A caller submits the inputs the bound skill works on and receives one deliverable back, in the contract's output shape (see `contract.yaml`). One unit of sale = one delivered result.

## Inputs — the codebase-visualization manifest

This atom does not render a diagram, draw a graph, read any
actual code, or exercise any judgment of its own. The caller
submits one JSON manifest declaring a visualization artifact
record — its declared diagram entries, its dependency view and
module counts, its call & flow views, its architecture map and
declared C4 levels, its metrics and history views with a
declared top hotspot, and its honesty record — and the atom
validates that artifact deterministically. Every field below is
read by the named section's checks. A field **absent** = evidence
missing (`INSUFFICIENT_EVIDENCE`); a field present but false /
invalid = the check fails (`CODEBASE_VISUALIZATION_NOT_READY`).
All fields are booleans unless noted.

Five checks are computed from the declared values, using only
what the skill itself states plus the arithmetic of the declared
numbers — no outside threshold is imported:

- **Diagram entries:** the entries check passes only when every
  declared diagram entry carries a non-empty `name`, `format`,
  `scope`, `generation_source` and `generated_at` string. A
  missing or empty list is missing evidence; an incomplete entry
  makes both computed diagram checks missing (the entry cannot be
  evaluated). The output reports `diagrams_evaluated` (the count
  of complete entries).
- **Diagram formats:** the skill's method step 1 names the
  diagrams-as-code tools — "Mermaid/Graphviz/PlantUML in the
  repo". The format check therefore passes only when every
  complete entry's declared `format` is one of `mermaid`,
  `graphviz`, `plantuml`. Entries are validated as strings only,
  never enum-checked at type level — format membership is a
  verdict check, not a type error.
- **Dependency coverage:** the declared
  `dependency.modules_included` passes only when it equals the
  declared `dependency.modules_total` (with a positive total —
  a zero total fails, as no graph over zero modules can be
  evaluated). The output reports `computed_dependency_coverage`
  (`modules_included` / `modules_total`, null when it cannot be
  computed) and `dependency_coverage_difference` (included minus
  total, null likewise). **No partial-coverage percentage is
  imposed** as a pass mark — only exact equality of the two
  declared counts.
- **C4 levels:** the skill's method step 4 states the C4-lite
  levels — context → containers → components. The declared
  `architecture.levels_declared` list therefore passes only when
  it contains all three stated entries (`context`, `containers`,
  `components`); extra entries do not hurt, unknown entries do
  not count toward coverage. A missing list is missing evidence;
  an empty list is present and fails. The output reports the
  omitted stated entries as `c4_levels_not_declared` (null when
  no list is declared). Entries are validated as strings only,
  never enum-checked — coverage is a verdict check, not a type
  error.
- **Hotspot score:** the skill's method step 5 defines hotspots
  as change-frequency × complexity. The declared
  `metrics.declared_hotspot_score` therefore passes only when it
  equals `metrics.hotspot_change_frequency` ×
  `metrics.hotspot_complexity`. The output reports
  `computed_hotspot_score` and `hotspot_score_difference`
  (declared minus computed, null when either cannot be
  computed).

**Fixed serialization rule:** computed amounts and ratios are
reported as strings with exactly six decimal places, produced in
both implementations by the same rule — round half up to 6dp,
`floor(v * 1000000 + 0.5) / 1000000`, then format with exactly six
decimals; computed comparisons compare the fixed-6dp difference
to zero. That fixed serialization is what makes the Python and
TypeScript outputs byte-identical.

The output also reports the computed `computed_status`
(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any of
the five computed checks cannot be completed).

The verdict is one of `CODEBASE_VISUALIZATION_READY` (all 32
checks pass), `CODEBASE_VISUALIZATION_NOT_READY` (any check
fails), or `INSUFFICIENT_EVIDENCE` (nothing fails but evidence
is missing), across six sections: diagrams_as_code,
dependency_views, call_and_flow_views, architecture_maps,
metrics_and_history_views, honesty_and_currency.

## Honest scoping

This atom audits a **declared** visualization artifact record —
it does not render graphics, generate a diagram, parse or read
actual code, build a dependency/call graph from a repository,
verify that a declared diagram exists in any repo, or verify
that a declared value is true. It exercises no judgment of its
own: the artifact declares its own views, coverage, encodings
and labels, and this core checks only their internal
consistency and the completeness of the skill's method on the
declared evidence. An artifact is ready *on the caller's
declared evidence* even if its diagrams are poor or its
codebase is tangled. It is a completeness and consistency
audit, **not a visualization review**: it never decides whether
a diagram is clear, whether an architecture map is accurate,
whether a hotspot deserves refactoring, or whether the declared
coverage matches the real codebase.

Named exclusions: no rendering or generation of any diagram; no
reading, indexing or parsing of any source code or repository;
no verification of any declared diagram, module count, cycle,
or label against a real codebase; no clarity, accuracy or
usefulness judgment of any view.

## Thresholds declined

The skill states no number for these, so none is imposed —
naming them here instead of inventing one:

- **No minimum diagram count** — the skill requires key diagrams
  as code in-repo, but states no number of diagrams; only entry
  completeness and stated formats are checked.
- **No partial dependency-coverage percentage** — no percentage
  (e.g. 80% or 90% of modules) is accepted as passing; only
  exact equality of the declared included and total counts.
- **No hotspot score cutoff** — the skill states the product
  formula (change-frequency × complexity) but no score above
  which a module counts as a hotspot; only the arithmetic is
  re-derived, and no refactor-target judgment is made.
- **No complexity or churn threshold** — no complexity value or
  change-frequency value is treated as high or low.
- **No diagram freshness age** — the skill requires a
  generated-at label and forbids stale diagrams shipped as
  truth, but states no maximum age in days; staleness is the
  caller's declaration (`stale_diagrams_shipped_as_truth`), and
  `generated_at` is checked as a non-empty label, never parsed
  or aged.
- **No allowable cycle or layering-violation count** — the skill
  requires cycles and violations to be visible, but states no
  permitted number; only their declared visibility is checked.
- **No coverage-overlay percentage, heatmap scale, or history
  window** — the skill names these views but states no coverage
  percentage, colour scale, or time window for them.

Design EXACTLY 4 cases:
1. kind "full-pass": an input manifest that satisfies every requirement the
   documents state, so the atom must return its PASS outcome (the pass
   verdict/status named in the documents).
2. kind "violations": a manifest of the same shape whose values are present
   but wrong in specific ways, so the atom must return its FAIL outcome and
   the checks covering those wrong values must fail. List the check names
   (as named in the documents/output format) you expect to fail.
3. kind "sparse": a manifest with only one or two fields present, so the
   atom must return its INSUFFICIENT_EVIDENCE outcome (or the equivalent
   named in the documents).
4. kind "malformed": a manifest with clear TYPE violations (e.g. a string
   where an object or list is required, a number where a boolean is
   required), so the atom must answer a clean input error (HTTP 422),
   never a 500 and never a verdict.

Inputs must follow the documented input format exactly (field names,
nesting, value types) — you are testing the atom, so your valid cases must
be genuinely valid per the documents. For computed/report atoms (whose
output is a computed artifact with a status such as complete / partial /
insufficient_evidence), adapt: full-pass = a complete well-formed input
expecting the complete status; violations = an input whose data violates
documented consistency rules expecting the documented failure/partial
behaviour; sparse = a minimal input expecting insufficient_evidence;
malformed = type violations expecting HTTP 422. Where the atom computes
numbers, add "computed_spot_checks" to the full-pass expect: a short list
of quantities the judge can recompute from the input by hand.
