# Negotiation preparation pack — `negotiation-preparation-pack`

**Deliverable type:** DELIVERABLE. This atom sells the deliverable it produces — a bounded judgment artifact — never the underlying knowledge itself.

## What it delivers

Bound capability (from the skill): Prepares the fundamentals and coaches the improvisation — real negotiation is nonlinear, and this skill handles both layers.

A caller submits the inputs the bound skill works on and receives one deliverable back, in the contract's output shape (see `contract.yaml`). One unit of sale = one delivered result.

The anchoring check is gated on the declared applicability
flag, exactly as declared: `anchoring_applicability_declared`
passes whenever `anchoring.informed_enough_to_anchor_first`
is present (either value). The gated check
`anchor_first_planned_when_informed` is **missing** when the
gate or the field itself is absent, **passes as not
applicable** when the gate is declared `false` (whatever the
field declares), and when the gate is declared `true` passes
only when the field is declared `true`.

Several checks are computed from the declared rows, using only
the skill's own stated rules plus the consistency of the
declared record itself — no outside threshold is imported:

- **Issues declared:** the declared `issues` list passes only
  when it is present and non-empty; an absent list is missing
  evidence, an empty list fails.
- **Own underlying interest per issue:** every declared issue
  row must name a non-empty `own_underlying_interest` string
  (the skill: "negotiate the underlying interest, not the
  stated demand"). A row with the field absent is missing
  evidence; a row naming an empty interest fails.
- **Counterpart underlying interest per issue:** every declared
  issue row must name a non-empty
  `counterpart_underlying_interest` string (the skill: "Ask
  *why* they want what they ask for"). A row with the field
  absent is missing evidence; a row naming an empty interest
  fails.
- **Trade potential assessed per issue:** every declared issue
  row must declare `trade_potential_assessed: true` (the
  skill: "Trade across issues you each value differently" —
  the check is that the assessment was made per issue, not
  what it found). A row with the field absent is missing
  evidence.
- **No issue name duplicated:** no declared issue `name` may
  appear on more than one issue row. A row with `name` absent
  is missing evidence for this check.

The output also reports the computed `computed_status`
(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any of
the five primary computed checks above cannot be completed),
`issues_count` (the declared list length, or null when the
list is not declared — counts are reported as integers,
exactly), the row-name lists `issues_without_own_interest`
(issues whose field is present but empty; an issue with the
field absent is missing evidence and does not appear),
`issues_without_counterpart_interest` (issues whose field is
present but empty) and
`issues_without_trade_potential_assessed` (issues whose field
is present but not true), `duplicate_issue_names` (issue names
declared on more than one row, in the order their second
occurrence appears), and the three coverage ratios
`own_interest_coverage` (issues naming the caller's own
underlying interest ÷ declared issues),
`counterpart_interest_coverage` (issues naming the
counterpart's underlying interest ÷ declared issues) and
`trade_potential_assessed_coverage` (issues with trade
potential assessed ÷ declared issues). **Fixed serialization
rule:** computed ratios are reported as strings with exactly
six decimal places, produced in both implementations by the
same rule — round half up to 6dp,
`floor(v * 1000000 + 0.5) / 1000000`, then format with exactly
six decimals; comparisons use the unrounded values. A ratio is
null when its denominator list is absent or empty. That fixed
serialization is what makes the Python and TypeScript outputs
byte-identical.

The skill states no numeric pass/fail threshold — its
preparation demands are qualitative declarations the record
makes, not bars the atom can set. Quantities are computed and
reported; the only bar on the computed rows is completeness
over the caller's own declared rows, exactly as stated above.
Declined thresholds, named: a reservation-price figure or a
minimum distance between the reservation price and any offer;
a ZOPA width or a minimum overlap between the two sides'
ranges; a BATNA strength, quality, or attractiveness score;
a number of issues a preparation must contain beyond the one
declared issues list being non-empty; a number of fallback
plans beyond the skill's own stated Plan B (and C); an
anchoring amount, percentage, or first-offer figure; a
coverage percentage below completeness; a debrief quality or
learning-outcome score.

The verdict is one of `NEGOTIATION_PREPARATION_SOUND` (all 44
checks pass), `NEGOTIATION_PREPARATION_NOT_SOUND` (any check
fails), or `INSUFFICIENT_EVIDENCE` (nothing fails but evidence
is missing), across five sections:
batna_reservation_price_and_zopa, interests_and_value_creation,
improvisation_and_adaptation,
openings_moments_closing_and_tactics,
debrief_and_anti_pattern_red_lines.

## Honest scoping

This atom reviews a **declared** negotiation-preparation
record — it prepares no negotiation itself, negotiates
nothing, coaches no live improvisation, reads no counterpart,
and does not verify that a declared preparation was ever
carried out. A preparation is sound *on the caller's declared
evidence*: a record that declares a strengthened BATNA, an
assessed ZOPA, and no rigid script passes those checks even if
the real preparation did none of it. It is a completeness and
consistency audit of the preparation record the skill
requires, **not negotiation advice, a negotiation service, or
a prediction that the negotiation will succeed**: it never
judges whether the declared BATNA is genuinely strong,
whether the reservation price is the right number, whether a
ZOPA truly exists, or whether the plan is good — only that the
record contains what the skill's fundamentals, improvisation,
tactics and anti-patterns demand, and that its declared issue
rows are internally consistent.

Named exclusions and non-reducible parts (carried as caller
declarations only, never judged): no numeric thresholds beyond
the skill's own stated rules (see the declined list above); no
live verification of any declared fact; no judgment of
preparation *quality* — whether the BATNA, interests, or
fallback plans will work is the caller's declaration, checked
only for declared presence and consistency; live improvisation
itself (presence of mind, situational awareness, recognizing
the pivot in the room) is by the skill's own account a live
act — this atom checks only that preparing for it is declared,
never the act; the skill's named pairings with other skills
(emotional-intelligence, psychological analysis) are not
invoked — composure and awareness are checked only as the
caller's own declared preparation in this record.
