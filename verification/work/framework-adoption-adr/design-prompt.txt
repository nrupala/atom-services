# Framework adoption adr — `framework-adoption-adr`

**Deliverable type:** DELIVERABLE. This atom sells the deliverable it produces — a bounded judgment artifact — never the underlying knowledge itself.

## What it delivers

Bound capability (from the skill): Adopt, structure, and upgrade frameworks deliberately — ADR for new ones, keep core framework-free, plan exits.

A caller submits the inputs the bound skill works on and receives one deliverable back, in the contract's output shape (see `contract.yaml`). One unit of sale = one delivered result.

## Buyer

First buyer hypothesis (from register data; not yet market-tested): teams and agents working in Engineering & code who need this deliverable on demand and would rather buy it per use than build or staff the capability themselves.

## Self-use (R3 — passed)

Our own workflow that calls it: **Product stack framework adoption decisions**. Wright is an internal caller on this atom (zero price, metered to the internal cost ledger — see `rails/billing.md`).

## Distinct ground vs the sibling `architecture-decision-record` atom

A live sibling, `architecture-decision-record`, audits a **general**
architecture decision record for completeness: NFRs written and
agreed, boundaries and contracts, an alternatives list of 2–3 with
trade-offs and at least one serious alternative, ADR format
(numbering, Context → Decision → Consequences → Status, one page
max), reversibility, security data flows, new-dependency reasons
and supersession. **This atom shares zero checks with it.** This
atom audits only the decision to **take on a framework**, on the
ground the bound `framework-discipline` skill alone states: the
adoption ADR's alternatives + exit-cost statement for *this
framework*, the five named fit criteria (team familiarity,
maintenance health, ecosystem, performance, exit cost) assessed
per candidate framework, exactly one candidate selected,
house-stack conformity (one framework per layer), a
framework-free core with the framework at the edges, exact
version pinning and major-upgrade planning, runtime
explicitness (lifecycle, DI, caching), plugin discipline and
deprecation handling. It has no alternatives count range, no
trade-offs/serious flags, no ADR format, numbering, page-count,
NFR, boundary, contract or supersession check; the sibling has
no fit-criteria, pinning, core-isolation, plugin or
framework-runtime check.

Several checks are computed from the declared rows, using only
the skill's own stated rules plus the consistency of the declared
record itself — no outside threshold is imported:

- **Candidates declared:** the declared `candidates` list passes
  only when it is present and non-empty; an absent list is
  missing evidence, an empty list fails.
- **Framework name per candidate:** every declared candidate
  row must name a non-empty `name` string. A row with the field
  absent is missing evidence; a row naming an empty string fails.
- **Fit fully assessed per candidate:** every declared candidate
  row must declare all five fit criteria from the skill's method
  step 1 assessed — `team_familiarity_assessed`,
  `maintenance_health_assessed`, `ecosystem_assessed`,
  `performance_assessed`, `exit_cost_assessed` all `true` (the
  skill: "Choose by fit: team familiarity, maintenance health,
  ecosystem, performance, and exit cost"). A row with any fit
  field absent is missing evidence.
- **Exactly one candidate selected:** exactly one declared
  candidate row may declare `selected: true` — an adoption ADR
  decides one framework, so zero or several selected rows are
  internally inconsistent on the declared evidence. A row with
  `selected` absent is missing evidence.
- **Every plugin reviewed and pinned:** when
  `plugins.plugins_present` is declared `true`, the declared
  `plugins.items` list must be present and non-empty and every
  row must declare `reviewed: true` and `pinned: true` (the
  skill: "plugins are dependencies — review, pin, and remove
  unused ones"). A row with either field absent is missing
  evidence. When no plugins are declared, the check passes as
  not applicable.

Three check groups are conditional, following the skill's own
scoping — computed from the declared gate fields:

- **Mid-project change:** `migration_plan_documented` and
  `migration_plan_approved` are required only when
  `house_stack.is_mid_project_change` is declared `true` (the
  skill: change mid-project = ADR + migration plan; red line: no
  framework-hopping mid-project without an *approved* migration
  plan); otherwise both pass as not applicable.
- **Major upgrade:** `major_upgrade_written_plan` and
  `major_upgrade_full_suite_run` are required only when
  `versions.major_upgrade_planned` is declared `true` (the
  skill's quality gate binds the written plan + full-suite run
  to major upgrades); otherwise both pass as not applicable.
- **Plugins:** the plugin-row and unused-plugin checks above are
  required only when `plugins.plugins_present` is declared
  `true`; otherwise both pass as not applicable.

The output also reports the computed `computed_status`
(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any of
the five primary computed checks above cannot be completed),
`candidates_count` and `plugins_count` (the declared list
lengths, or null when a list is not declared — counts are
reported as integers, exactly), `selected_count` (declared
selected candidate rows, or null when the candidates list is not
declared), `selected_candidate` (the sole selected candidate's
name, or null when there is not exactly one selected row with a
non-empty name), the row-name lists `candidates_without_name`
(null when the list is not declared),
`candidates_without_fit_assessment` (rows with at least one fit
field present but not all five assessed; a row with no fit field
present is missing evidence and does not appear) and
`plugins_without_review_or_pin` (plugin rows with `reviewed` or
`pinned` present but not both true; a row with both absent is
missing evidence and does not appear), and the two coverage
ratios `fit_assessment_coverage` (candidates with all five fit
criteria assessed ÷ declared candidates) and
`plugin_compliance_coverage` (plugins declaring reviewed and
pinned ÷ declared plugins).
**Fixed serialization rule:** computed ratios are reported as
strings with exactly six decimal places, produced in both
implementations by the same rule — round half up to 6dp,
`floor(v * 1000000 + 0.5) / 1000000`, then format with exactly six
decimals; comparisons use the unrounded values. A ratio is null
when its denominator list is absent or empty. That fixed
serialization is what makes the Python and TypeScript outputs
byte-identical.

The skill states no numeric pass/fail threshold — no exit-cost
amount, no fit score, no maintenance-health metric, no upgrade
cadence: its fit criteria and exit cost are judgments the record
attests to having made, not bars the atom can set. Quantities
are computed and reported; the only bar on the computed rows is
completeness over the caller's own declared rows, exactly as
stated above. Declined thresholds, named: an exit-cost amount or
ceiling (the skill requires exit cost to be stated/assessed but
states no number — caller declaration only); a fit score or
weighting across the five criteria (the skill names the criteria
but states no score, weight or minimum — assessment declared,
quality not scored); a maintenance-health metric (commits,
release cadence, issue latency — the skill says "maintenance
health" but states no measure); a candidate-count range (the
skill requires alternatives in the ADR but states no number for
framework candidates — unlike the sibling skill's 2–3 general
alternatives rule, which is *not* imported here; completeness
and exactly-one-selected are the only bars); an upgrade cadence
or batch size (the skill says "batch updates" but states no
interval or size); a deprecation-migration window (the skill
says "migrate on schedule" but states no period); a codemod
requirement as a separate check (the skill lists codemods among
upgrade tools — "use codemods" states no condition under which
one is mandatory, so no check is invented for it; the written
plan + full-suite run quality gate is the checkable bar).

The verdict is one of `FRAMEWORK_ADOPTION_SOUND` (all 30 checks
pass), `FRAMEWORK_ADOPTION_NOT_SOUND` (any check fails), or
`INSUFFICIENT_EVIDENCE` (nothing fails but evidence is missing),
across five sections: adr_and_fit, house_stack_and_core,
pinning_and_upgrades, explicitness_and_runtime,
plugins_and_deprecations.

## Honest scoping

This atom audits a **declared** framework-adoption record — it
writes no ADR, chooses no framework, inspects no codebase for
framework imports, reads no lockfile, and does not verify that a
declared control actually works. An adoption is sound *on the
caller's declared evidence*: a manifest that declares a logged
ADR with exit cost, a framework-free core and pinned versions
passes those checks even if the real project does none of it. It
is a completeness and consistency audit of the record the skill
requires, **not a framework selection service or a live posture
certification**: it never judges whether the selected framework
is the right choice commercially, whether a declared fit
assessment was well made, whether the real core is truly
framework-free, or whether a declared exit cost is realistic —
only that the record contains what the skill's sections and red
lines demand, and that its declared rows are internally
consistent.

Named exclusions: no numeric thresholds beyond the skill's own
stated rules (see the declined list above); no live verification
of any declared fact; no code, repository or lockfile inspection
(core framework imports, version pinning and zombie code paths
are caller declarations, the atom reads no code); fit judgment
(which framework *should* be selected, how the five criteria
should be weighted) is a caller declaration — the atom checks
only that every candidate was assessed on all five criteria and
that exactly one is selected, never which candidate ought to
win; the skill's preference for boring and stable over
fashionable is carried as the caller's own fit assessment, not
scored here (and is not duplicated from the sibling atom's
boring-technology check); the skill's cross-references to
sibling disciplines (`architecture-decisions` for the ADR form
itself, `dependency-governance` for plugin/dependency depth,
`typescript-engineering`) are carried as the caller's own
attestations in this record, not re-audited here — the ADR's
*general* completeness belongs to the sibling
`architecture-decision-record` atom.

## Named doubt (from the register)

Advice plus ADR, easily replicated


Design EXACTLY 4 cases:
1. kind "full-pass": an input manifest that satisfies every requirement the
   documents state, so the atom must return its PASS outcome (the pass
   verdict/status named in the documents).
2. kind "violations": a manifest of the same shape whose values are present
   but wrong in specific ways, so the atom must return its FAIL outcome and
   the checks covering those wrong values must fail. List the check names
   (as named in the documents/output format) you expect to fail.
3. kind "sparse": a manifest with only one or two fields present, so the
   atom must return its INSUFFICIENT_EVIDENCE outcome (or the equivalent
   named in the documents).
4. kind "malformed": a manifest with clear TYPE violations (e.g. a string
   where an object or list is required, a number where a boolean is
   required), so the atom must answer a clean input error (HTTP 422),
   never a 500 and never a verdict.

Inputs must follow the documented input format exactly (field names,
nesting, value types) — you are testing the atom, so your valid cases must
be genuinely valid per the documents. For computed/report atoms (whose
output is a computed artifact with a status such as complete / partial /
insufficient_evidence), adapt: full-pass = a complete well-formed input
expecting the complete status; violations = an input whose data violates
documented consistency rules expecting the documented failure/partial
behaviour; sparse = a minimal input expecting insufficient_evidence;
malformed = type violations expecting HTTP 422. Where the atom computes
numbers, add "computed_spot_checks" to the full-pass expect: a short list
of quantities the judge can recompute from the input by hand.

Return JSON only, exactly this shape:
{"cases": [
