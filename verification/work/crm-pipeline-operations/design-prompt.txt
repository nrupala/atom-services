# CRM pipeline operations — `crm-pipeline-operations`

**Deliverable type:** DELIVERABLE. This atom sells the deliverable it produces — a bounded judgment artifact — never the underlying knowledge itself.

A caller submits the inputs the bound skill works on and receives one deliverable back, in the contract's output shape (see `contract.yaml`). One unit of sale = one delivered result.

## Inputs — the CRM pipeline manifest

This atom does not operate a CRM, contact anyone, or move a
deal, and exercises no judgment of its own. The caller submits
one JSON manifest declaring a CRM pipeline-operations artifact
— its single-source and hygiene record, its contact-rule and
privacy record, its declared pipeline stages with entry/exit
criteria, its declared deal rows, its follow-up cadence and
logging record, its reporting and forecast record, its consent
record, its win/loss record, and its minimal-data/retention
record — and the atom validates that artifact deterministically.
Every field below is read by the named section's checks. A field
**absent** = evidence missing (`INSUFFICIENT_EVIDENCE`); a field

Five checks are computed from the declared values, using only
what the skill itself states plus the arithmetic of the declared
rows and the caller's own declared limit — no outside threshold
is imported:

- **Pipeline stages:** the skill's method step 3 names the
  pipeline — lead → qualified → proposal → decision → won/lost.
  The declared `pipeline.stages_used` list therefore passes only
  when it contains all six stated entries (`lead`, `qualified`,
  `proposal`, `decision`, `won`, `lost`); unknown entries do not
  count toward coverage. A missing list is missing evidence; an
  empty list is present and fails. The output reports the
  omitted stated entries as `pipeline_stages_not_covered` (null
  when no list is declared). Entries are validated as strings
  only, never enum-checked — coverage is a verdict check, not a
  type error.
- **Deal rows complete:** every declared deal row must carry
  `stage` (non-empty string), `value`, `age_days`,
  `has_next_step`, `has_next_step_date`, and `open`. A non-empty
  list with an incomplete row is missing evidence for every
  row-derived check (that row cannot be evaluated); an empty
  list is present and fails — no rows exist to prove anything
  over.
- **Deal stages are stated stages:** every complete row's
  `stage` must be one of the six stages the skill names.
- **Next step + date:** the skill's quality gate is "Next-step
  + date on every open deal". Every declared row with
  `open = true` must therefore declare both `has_next_step` and
  `has_next_step_date`; closed rows are not counted. The output
  reports `open_deals_without_next_step_or_date_count`. A zero
  open-deal count fails — no open pipeline exists to prove this
  over.
- **Staleness against the caller-declared window:** the skill
  says stale contacts/deals are "flagged, not trusted" and the
  stuck-deal list is reviewed, but it states **no day count**.
  An open deal is therefore counted stale only when its
  declared `age_days` exceeds the caller's own declared
  `pipeline.stale_threshold_days` (an age exactly equal to the
  threshold is not stale; closed deals are not counted). The
  check passes only when the stale count is zero, and a zero
  open-deal count fails as above. The output reports
  `stale_deal_count` (null when the rows or the threshold cannot
  be evaluated).

The output also reports, from the complete declared rows only
(all null when the rows cannot be evaluated, except `deal_count`
which is the declared list length whenever a list is declared):
`deal_count`, `open_deal_count`, `stage_distribution` (counts
per stated stage, in stated-stage order),
`computed_open_value_total` (sum of `value` over open rows) and
`computed_pipeline_value_total` (sum of `value` over all rows).

**Fixed serialization rule:** computed amounts are reported as
strings with exactly six decimal places, produced in both
implementations by the same rule — round half up to 6dp,
`floor(v * 1000000 + 0.5) / 1000000`, then format with exactly six
decimals. Counts and the stage distribution are reported as
plain integers (null when they cannot be computed). That fixed
serialization is what makes the Python and TypeScript outputs
byte-identical.

The output also reports the computed `computed_status`
(`within_stated_limits_on_declared_evidence` /
`outside_stated_limits_on_declared_evidence` / null when any of
the five computed checks cannot be completed).

The verdict is one of `CRM_PIPELINE_READY` (all 38 checks
pass), `CRM_PIPELINE_NOT_READY` (any check fails), or
`INSUFFICIENT_EVIDENCE` (nothing fails but evidence is missing),
across eight sections: single_source_of_truth,
contact_rules_and_privacy, pipeline_stages_and_deals,
follow_up_cadence_and_logging, reporting_and_forecasts,
consent_and_comms, win_loss_discipline,
minimal_data_and_retention.

## Honest scoping

This atom audits a **declared** CRM pipeline-operations
artifact — it does not operate a CRM, contact anyone, send or
draft outreach, move a deal, verify that a declared value is
true, or judge whether relationships are actually well run. The
register's named doubt for this atom — contact privacy rules
apply — is answered by this framing: the artifact declares
counts, deal-row facts, and process facts only; no contact's
personal data is an input, and this core reads none. An artifact
is ready *on the caller's declared evidence* even if its actual
pipeline is poor. It is a completeness and consistency audit,
**not a CRM-quality review**: it never decides whether a next
step is meaningful, whether a follow-up touch really carried
value, whether a forecast probability is actually honest,
whether entry/exit criteria are well written, or whether a
win/loss reason is insightful — those load-bearing judgments in
the skill cannot be reduced to deterministic checks and are
carried only as caller-declared booleans here.

**Thresholds declined (named explicitly):** the skill states no
staleness day count, so none is imposed — only the caller's own
declared `stale_threshold_days` is applied; the skill says
dedupe happens "on a schedule" but states no period, so no
dedupe frequency is imposed; the skill says follow-ups are
"scheduled" and the stuck-deal review is held "on cadence" but
states no interval for either, so none is imposed; the skill
calls for conversion rates by stage "(base rates!)" but states
no target rate, and a per-stage conversion rate cannot be
re-derived from current-stage deal rows (rows show where deals
are, not the flow that entered and left each stage), so no
conversion value is computed or judged — reporting them is
checked as a declared boolean only; the skill states no
retention period for dead leads, so only that retention is
*defined* is checked, never its length; the skill states no
minimum deal count, pipeline value, or open-deal value, so none
is imposed (the zero-open-deal failure above is a proof-existence
rule, not a size threshold); the skill states no forecast
probability or calibration threshold, so none is imposed.

Named exclusions: no operating a CRM or any other system; no
outreach, drafting, or contact of any kind; no verification of
any declared count, value, stage, or process claim; no
next-step-quality, touch-value, criteria-quality,
probability-honesty, or win/loss-insight judgment; no live
verification of any declared fact.
